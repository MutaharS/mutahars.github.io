A search engine from crawl to ranked result.

I built this prototype to understand the full retrieval path: discover pages, extract text, turn content into an index, and return useful results for a query.

View the source on GitHub ↗

The problem I wanted to understand

Search looks simple from the outside: type a phrase and get relevant pages. Underneath it is a chain of decisions about what to crawl, how to represent text, what should count as relevant, and how to retrieve results quickly. I wanted to build that chain myself rather than treat search as a black box.

How the prototype works

1. Crawl and extract

The crawler starts from a seed URL, follows discovered HTTP links, and uses Requests and BeautifulSoup to extract paragraph text. It tracks visited and unvisited URLs in JSON files, caps visits per domain, and uses timeouts and checkpoints to keep a long run manageable.

2. Build the index

The indexing notebook uses PySpark RDD transformations to calculate term frequency and document frequency, then computes TF-IDF scores for terms within documents. It computes scores for single terms and two- and three-word phrases, then builds term-to-URL lookup data ordered by score. The query notebook demonstrates single-term and two-word retrieval.

3. Retrieve ranked links

The search notebook tokenizes a query, looks up matching terms or two-word phrases, and returns links ordered by their stored relevance score. The result is a working demonstration of an inverted index and ranked retrieval, rather than a production search service.

What I learned

The project made the cost of each boundary concrete: crawling can be noisy, tokenization changes what can be found, indexing choices shape query latency, and a ranking formula is only as useful as the documents and evaluation behind it. Building the full path gave me a much stronger intuition for data structures, distributed processing, and information retrieval.

What I would change today

  • Canonicalize URLs and handle duplicate or low-value pages before indexing.
  • Make the crawler respect site policies and strengthen retries, error handling, and reproducible runs.
  • Keep document-frequency data distributed or in a scalable store instead of collecting it to the driver.
  • Add query deduplication, relevance tests, and a small service interface to make the prototype easier to use and evaluate.

This is a prototype and a technical learning project. The linked notebooks show the implementation and its current limits.
